Architektur

Statisches Frontend, gesichertes Backend

GitHub Pages liefert nur statische Dateien. Alle Daten, Logins und Berechtigungen liegen daher in Supabase (Free Tier): Postgres mit Row-Level-Security, Supabase Auth und eine Edge Function für das Zugangspasswort.

Browser (SPA, Hash-Routing)
│ HTTPS · JWT
▼
Supabase REST/RPC ──► Postgres + RLS
Edge Function ──► Zugangscode-Prüfung

Im Client steht nur der öffentliche anon key – er gewährt ohne gültige Session und passende RLS-Policy keinerlei Datenzugriff.

Privat & unauffindbar

Zugangspasswort + kein Index

  • Zugangspasswort wird serverseitig in einer Edge Function geprüft (Hash als Secret, Rate-Limit). Ohne gültigen Code ist keine Registrierung möglich.
  • Ehrlich: Eine Passwortseite auf GitHub Pages kann die statischen Dateien selbst nicht verbergen. Darum ist die App-Hülle bewusst inhaltsleer – alle Daten gibt es nur mit Login + RLS.
  • <meta name="robots" content="noindex,nofollow">, robots.txt: Disallow /, keine Sitemap, keine Open-Graph-Vorschau.
  • Hinweis: Pages im Free-Plan erfordert ein öffentliches Repo. Der Code enthält keine Geheimnisse.

Login & Konten

Username + Passwort, ohne E-Mail

  • Supabase Auth mit interner Pseudo-Adresse <username>@users.invalid, E-Mail-Bestätigung aus. Der Nutzer sieht nur seinen Username.
  • Username: 3–24 Zeichen, a–z 0–9 _ ., eindeutig (case-insensitive).
  • Passwort: mind. 12 Zeichen, nicht = Username, Abgleich gegen geleakte Passwörter (HIBP, k-Anonymität), Stärkeanzeige.
  • Kurzlebige JWTs, Refresh-Token-Rotation, Sperre/Backoff nach Fehlversuchen, einheitliche Fehlermeldung „Username oder Passwort falsch“.

OWASP Top 10 (2021/2025) – Gegenmaßnahmen

A01

Zugriffskontrolle: RLS auf jeder Tabelle, Default-Deny. Nur Gruppenmitglieder lesen Gruppe/Wünsche; Claims sind für den Wunsch-Owner per Policy unsichtbar.

A02

Kryptografie: nur HTTPS (Pages-Enforce), Passwörter bcrypt in Supabase, Zugangscode als Argon2id-Hash.

A03

Injection/XSS: parametrisierte Queries, Zod-Validierung client- & DB-seitig (CHECK-Constraints), React-Escaping, kein dangerouslySetInnerHTML, Links nur https: mit rel="noopener noreferrer nofollow".

A04

Unsicheres Design: Threat-Model, Überraschungsschutz in der DB statt in der UI, Einladung erfordert Annahme.

A05

Fehlkonfiguration: strikte CSP per Meta-Tag (nur self + Supabase-Host), keine Inline-Skripte, Referrer-Policy no-referrer, Frame-Busting (Pages erlaubt keine eigenen Header).

 

A06

Komponenten: Dependabot, npm audit in CI, Lockfile, minimale Abhängigkeiten.

A07

Authentifizierung: Mindestanforderungen, Rate-Limits, keine Username-Enumeration beim Login; Usersuche fürs Einladen nur eingeloggt, nur exakter Treffer, gedrosselt.

A08

Integrität: GitHub Actions mit per SHA gepinnten Actions, Deploy nur von main, Branch-Protection, SRI für alles Externe.

A09

Logging: Supabase Auth-Audit-Log, fehlgeschlagene Zugangscode-Versuche werden protokolliert.

A10

SSRF: keine serverseitige Link-Vorschau; Produkt-Links werden nie vom Server abgerufen.

+

Darüber hinaus: CSRF entfällt (Bearer-Token statt Cookies), Clickjacking-Schutz, Konto löschen inkl. aller Daten (DSGVO), Beträge als Integer-Cent.
